# TSK_00008 — Módulo Fiscal NFC-e (SEFAZ-SP, homologação)

Fonte: `docs/general.md` §24–840 ("Implementação do módulo fiscal NFC-e
— SEFAZ-SP").

## Objetivo

Fundação do módulo fiscal modelo 65 para SEFAZ-SP em **homologação**:
domínio, chave de acesso, geração de XML (leiaute 4.00), assinatura A1,
cliente SEFAZ com idempotência, persistência e DANFE (dados + QR Code).
Contingência e produção ficam explicitamente fora (§17/§24).

## App

`apps/fiscal` — isolado; o resto do sistema só fala com `FiscalService`.

## Dependências novas

- `cryptography` — carregar certificado A1 (PFX/P12)
- `signxml` (+lxml) — XMLDSig-RSA-SHA256 conforme padrão NF-e
  (proibido implementar criptografia própria)
- `requests` — SOAP/HTTPS com timeout

## Componentes (responsabilidade única)

```
chave.py          ChaveAcesso: montagem 43 dígitos + DV mod-11,
                  validação (testes com vetores oficiais)
xml_builder.py    NFCeBuilder → ElementTree leiaute 4.00
                  (ide/emit/dest/det/prod/ICMS20/total/transp/pag/
                  infAdic); sem valores fictícios — falta de dado
                  obrigatório levanta FiscalError
certificate.py    CertificateProvider A1: carregar PFX, validar
                  validade, expor key/cert; erros claros; nunca logar
                  segredo
signing.py        XMLSigner (signxml) assinando infNFe, C14N,
                  RSA-SHA256
sefaz/client.py   SefazClient ABC: status_servico, autorizar,
                  consultar_protocolo, receber_evento, inutilizar
sefaz/sp.py       SefazSPClient homologação: URLs oficiais centralizadas
                  por UF/ambiente, envelope SOAP, TLS+cert, timeout;
                  HTTP 200 ≠ autorizado — decide pelo conteúdo
sefaz/parser.py   SefazResponseParser → RetornoSefaz(dataclass:
                  cstat, xmotivo, protocolo, xml...) ; rejeição vs erro
service.py        FiscalService.emitir_nfce(venda): gerar→validar→
                  assinar→transmitir→persistir; consultar_nfce(chave);
                  cancelar(chave, justificativa); inutilizar(...);
                  status_sefaz()
danfe.py          DanfeRenderer: dados estruturados + QR Code URL
                  (spec vigente CSC) — documento ≠ impressão
```

## Idempotência (obrigatória)

Timeout/resposta perdida após transmissão: NFCe fica TRANSMITINDO com
chave persistida ANTES do envio; reprocesso consulta a chave na SEFAZ
antes de gerar nova numeração. Nunca emite segunda NFC-e para a mesma
venda (unique venda+status ativo).

## Settings

`SEFAZ_UF=SP`, `SEFAZ_AMBIENTE=HOMOLOGACAO` (default; PRODUCAO exige
config explícita e bloqueia testes), `SEFAZ_TIMEOUT`,
`SEFAZ_CERTIFICATE_PASSWORD`. UI admin exibe "AMBIENTE DE HOMOLOGAÇÃO".

## Testes (sem rede real)

- chave/DV: vetores conhecidos, validação, chave inválida
- builder: XML contém nós obrigatórios, valores da venda, rejeita dado
  ausente
- certificate: PFX de teste gerado on-the-fly (cryptography), expirado
  detectado
- signing: XML assinado valida criptograficamente (signxml verify)
- parser: fixtures de resposta autorização/rejeição/erro SOAP
- service: fluxo com SefazClient fake (autorizado, rejeitado, timeout→
  consulta recupera protocolo, não duplica NFC-e)
- danfe: campos e URL do QR code

## Critérios de aceite cobertos

Cenários 2–5, 8, 11, 12 automatizados; cenários 6–7 (transmissão real
homologação) exigem certificado/credenciamento — estrutura pronta,
execução manual documentada.

## Fora de escopo

Contingência, produção, NF-e modelo 55, impressora térmica/agente local.
